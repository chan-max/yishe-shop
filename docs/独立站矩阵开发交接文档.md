# 衣设独立站矩阵开发交接文档

文档版本：2026-07

## 1. 项目定位

本仓库是一个基于 Nuxt 4 的独立站矩阵。目标是：

- 在同一个 monorepo 内维护多个面向不同品类、品牌和域名的独立站。
- 将商品、账号、认证、SEO、图片、设计需求等通用能力放在根目录复用。
- 将品牌文案、导航、主题、首页内容和品类页面留在具体站点中独立演进。
- 每个 `apps/*` 都可以单独开发、构建和部署，不互相共享页面视觉。

当前代码同时存在两种站点层：

1. `apps/*`：按域名/业务独立的 Nuxt App，当前三个线上独立站主要使用这一层。
2. `sites/*`：面向配置驱动品牌层的抽象，已经用于根核心的 SEO、主题和共享首页组件，后续新矩阵站点应逐步采用。

## 2. 当前站点矩阵

| App | 业务定位 | 本地开发端口 | 站点配置域名 | 生产 PM2 端口 |
| --- | --- | ---: | --- | ---: |
| `apps/shop-main` | 衣设主站、POD 商品和在线设计 | `15201` | `shop-main.1s.design`（配置默认值） | `15201` |
| `apps/shop-business-card` | Gucci 风格商务名片独立站 | `15202` | `card.1s.design`（页面/配置默认值） | `15203` |
| `apps/shop-couplets` | 春联、楹联定制独立站 | `15204` | `couplets.1s.design`（配置默认值） | `15205` |

生产域名、反向代理和 PM2 配置在服务器侧维护。GitHub Actions 当前会在 `main` 分支 push 后构建并部署三个 App。

## 3. 目录职责

```text
.
├── apps/                         # 独立站入口，每个 App 有自己的 pages/config
│   ├── shop-main/
│   ├── shop-business-card/
│   └── shop-couplets/
├── sites/                        # 品牌配置层和可复用品牌组件
│   ├── index.ts                  # siteRegistry + activeSiteConfig
│   ├── types.ts                  # SiteDefinition 类型契约
│   └── yishe/                    # 当前默认品牌配置
├── components/                   # 跨站通用 UI 组件
├── composables/                  # 跨站业务能力
├── stores/                       # Pinia 全局状态
├── utils/                        # API、请求、SEO、图片、商品 URL 等基础能力
├── middleware/                   # 认证等通用路由中间件
├── server/                       # API 代理、sitemap 和服务端路由
├── pages/                        # 根层/历史页面，修改前先确认是否被 App 继承
├── assets/                       # 全局样式和静态素材
└── .github/workflows/nuxtjs.yml # 三个独立站的 CI/CD
```

### 修改边界

- 品牌名称、域名文案、首页内容、导航、页脚、颜色和字体：放在 `apps/<site>` 或 `sites/<site>`。
- 商品列表、商品详情、账号认证、收藏、设计需求、图片处理、SEO serializer、sitemap：优先放在根 `composables/`、`stores/`、`utils/`、`server/`。
- 不要在每个站点复制 API client、Pinia store、登录 token 逻辑和商品归一化逻辑。
- 修改根 `pages/` 前要确认影响范围；根页面可能会被所有 `apps/*` 继承或参与路由生成。

## 4. 核心共享能力

### 商品

文件：`composables/use-published-products.ts`

- `fetchPublishedProducts(options)`：调用 `/product/page`，默认只取已发布且有图片的商品。
- 支持参数：`pageSize`、`searchText`、`type`、`category`、`random`。
- 返回统一的 `StorefrontPublishedProduct`：
  `id`、`title`、`description`、`category`、`type`、`imageUrl`、`code`、`slug`、`creator`、`price`、`originalPrice`。
- `getPublishedProductImage(product, width)`：统一生成预览图 URL。
- `getPublishedProductPath(product)`：统一商品 URL。
- `fetchProductDetail(id)`：调用 `/product/:id` 获取详情。

注意：后端原始字段通常是 `name`、`images`、`salePrice`；页面层应使用归一化后的 `title`、`imageUrl`、`price`，不要重新读取 `item.name` 或 `item.images`。

### 设计需求

文件：`composables/use-design-request.ts`

`submitDesignRequest({ name, description, phoneNumber, email })` 调用 `/design-request`。定制表单、免费设计申请和商品详情页都应复用该方法，不使用 `alert` 假装提交成功。

### 用户认证

文件：`stores/public-user.ts`、`utils/api.ts`、`utils/request.ts`

- token 存储键：`public-user-token`。
- 用户资料存储键：`public-user-info`。
- 页面进入后调用 `publicUserStore.initToken()` 恢复登录状态。
- 登录成功后调用 `setToken()`，再调用 `/public-user/getUserInfo` 并调用 `setUserInfo()`。
- 退出登录调用 `api.publicUser.logout()`，无论接口是否成功都必须执行 `clearToken()`。
- `request.ts` 会自动附带 `Authorization: Bearer <token>` 和 Open API Key。

主要接口：

| 功能 | 方法 |
| --- | --- |
| 注册 | `POST /public-user/register` |
| 登录 | `POST /public-user-auth/login` |
| 获取用户信息 | `POST /public-user/getUserInfo` |
| 退出 | `POST /public-user-auth/logout` |
| 更新资料 | `POST /public-user/update` |
| 设计申请 | `POST /design-request` |
| 商品分页 | `POST /product/page` |
| 商品详情 | `GET /product/:id` |

## 5. 品牌配置层 `sites/`

`sites/types.ts` 定义 `SiteDefinition`，包括品牌、URL、SEO、导航、页脚、功能开关、主题和首页内容。`sites/yishe/` 是当前默认实现，品牌组件会以 `Site` 前缀自动注册，例如：

```vue
<SiteProductCard />
```

注册新品牌的基础步骤：

1. 复制 `sites/yishe` 为 `sites/<site-id>`。
2. 修改 `site.config.ts`、`content/home.ts`、`theme/tokens.css` 和品牌组件。
3. 在 `sites/index.ts` 注册到 `siteRegistry`。
4. 为部署环境配置 API、Open API Key、站点 URL。

当前 `activeSiteConfig` 在 `sites/index.ts` 中固定为 `siteRegistry.yishe`，属于构建期单一激活配置，不是运行时多租户切换。新增独立域名时，必须确认该站点的根 SEO、sitemap、主题和 `app.vue` 是否仍然读取 yishe 配置。

如果新站点需要完全独立的页面和域名，优先新增 `apps/shop-<site>`；如果只是同一套平台换品牌内容，优先扩展 `sites/<site-id>`。两者不要同时复制同一套业务逻辑。

## 6. 独立站 App 开发流程

### 新增一个独立站

1. 创建 `apps/shop-<site-id>/`，至少包含 `package.json`、`nuxt.config.ts` 和 `pages/`。
2. 在 `nuxt.config.ts` 中使用 `extends: [resolve(currentDir, '../../')]`。
3. 分配唯一开发端口和生产端口。
4. 设置站点 `url`、`name`、`description`、`siteName`、`adminId`。
5. 页面内使用 `useSeoMeta` / `useHead` 覆盖该站点的品牌 SEO。
6. 商品、登录、注册、设计申请统一调用根目录 composables/API/store。
7. 增加移动端断点，检查 Header、商品网格、表单、Footer 是否横向溢出。
8. 在根 `package.json` 增加 `dev:<site>`、`build:<site>` 脚本。
9. 在 `.github/workflows/nuxtjs.yml` 增加构建、产物检查、上传和 PM2 重启步骤。
10. 配置反向代理、域名证书和服务器 PM2 进程后再上线。

### 本地命令

仓库同时存在 `pnpm-workspace.yaml`、`pnpm-lock.yaml` 和 `package-lock.json`。CI 当前使用 npm，因此交接和发布环境优先使用 npm，避免随意更新两套 lockfile。

```bash
npm ci

# 启动单个站点
npm run dev:main
npm run dev:card
npm run dev:couplet

# 独立构建
npm run build:main
npm run build:card
npm run build:couplet

# 三站点构建
npm run build:all
```

默认本地地址：

- 主站：`http://localhost:15201`
- 名片站：`http://localhost:15202`
- 春联站：`http://localhost:15204`

## 7. 环境变量与 API

常用变量：

| 变量 | 用途 |
| --- | --- |
| `NUXT_PUBLIC_API_BASE` | API 基础地址；开发默认 `http://localhost:1520/api` |
| `NUXT_PUBLIC_OPEN_API_KEY` | 商品和开放接口所需 Open API Key |
| `NUXT_PUBLIC_SITE_URL` | 站点规范 URL、SEO 和 sitemap |
| `NUXT_PUBLIC_SITE_NAME` | 主站站点名称 |
| `NUXT_PUBLIC_ADMIN_ID` | 站点归属主账号标识 |
| `NITRO_OUTPUT_DIR` | 覆盖 Nitro 构建产物目录 |
| `NUXT_BUILD_DIR` | 覆盖 Nuxt 构建缓存目录 |
| `NUXT_VITE_CACHE_DIR` | 覆盖 Vite 缓存目录 |

不要把私有密钥提交到站点配置或页面。Open API Key 属于前端可见的公开绑定凭据，仍应通过部署环境注入并按站点隔离。

## 8. CI/CD 与生产部署

工作流：`.github/workflows/nuxtjs.yml`

触发条件：push 到 `main`，或手动 `workflow_dispatch`。

当前流程：

1. Node 20 + `npm ci`。
2. 构建主站、名片站、春联站。
3. 检查三个 `.output/server/index.mjs` 是否存在。
4. 为三个产物打包并上传到腾讯云。
5. 服务器解压到各自网站目录。
6. 使用 PM2 启动或重启三个 SSR 进程并 `pm2 save`。

生产端口和 PM2 名称：

| 站点 | PM2 名称 | 端口 |
| --- | --- | ---: |
| 主站 | `yishe-shop` | `15201` |
| 名片站 | `yishe-shop-business-card` | `15203` |
| 春联站 | `yishe-shop-couplet` | `15205` |

修改 CI 时要同时检查产物目录：主站输出在根 `.output`，名片站和春联站输出在各自 `apps/*/.output`。不要把三站点产物混在同一个目录。

## 9. SEO 与路由约定

- 页面级标题和描述：在站点页面使用 `useSeoMeta` 和 `useHead`。
- 根站点默认 SEO：由 `utils/seo.ts` 从 `activeSiteConfig` 生成。
- sitemap：`server/routes/sitemap.xml.get.ts`、`server/routes/sitemaps/` 和商品 URL 生成器共同负责。
- 登录、注册、个人资料、收藏、搜索等非 SEO 页面应保持 sitemap 排除。
- 商品 URL 优先使用 `getPublishedProductPath()`；如果 App 只实现 `/product/[id]`，不要生成带 slug 的 URL，或同时增加对应动态路由。
- 页面标题、OG 描述、站点域名和 canonical URL 不要复制主站文案到其他独立站。

## 10. UI 与响应式交接约定

- 业务站点可以拥有完全不同的视觉风格，但功能入口要保留：登录/注册、商品搜索、商品详情、定制申请、用户退出。
- 移动端至少检查 `640px`、`768px`、`900px` 三个区间；商品网格、Banner、Header、表单和底部导航不应横向溢出。
- 首页主视觉只使用当前站点商品素材；不要添加与商品无关的装饰图。
- 黑白或低彩色品牌站点避免引入无关渐变、阴影和过大的标题。
- 搜索输入和表单使用无默认 outline 的扁平样式时，仍需保留可识别的焦点状态，不能让键盘用户完全失去定位。

## 11. 交付检查清单

提交前：

- [ ] 只修改了目标 App 或明确的根共享模块。
- [ ] 商品字段使用 `title` / `imageUrl` / `price`，没有重新读取原始 `name` / `images`。
- [ ] 登录成功写入 token 和 userInfo，退出登录调用 `clearToken()`。
- [ ] 定制表单调用 `useDesignRequest()`，没有使用假 `alert` 成功提示。
- [ ] 页面 SEO、站点 URL、favicon 和 OG 文案属于当前独立站。
- [ ] 手机端 Header、照片墙/商品网格、按钮、输入框和 Footer 没有溢出。
- [ ] `git diff --check` 通过。
- [ ] 按需要执行目标站点构建；生产发布前执行 `npm run build:all`。
- [ ] 检查 CI 产物路径和 PM2 端口没有冲突。

## 12. 已知风险与后续建议

- 当前 `activeSiteConfig` 是固定 yishe，根 `app.vue` 和 `utils/seo.ts` 仍可能为新 App 提供 yishe 默认值。长期应改为每个 App 显式注入自己的 site definition，或将站点选择纳入构建变量。
- 三个 App 的页面结构仍有一部分历史独立实现，通用能力已经抽离，但 Header、Footer 和部分商品展示仍存在重复 CSS。后续可抽取无品牌的 `AccountMenu`、`ProductCard`、`ProductGallery` 基础组件。
- 根目录同时保留旧页面和新 App 页面，新增路由前先确认 Nuxt layer 的路由合并结果，避免同路径覆盖。
- CI 目前一次构建三个站点，任何一个站点构建失败都会阻止全部部署；矩阵扩大后应改为 GitHub Actions matrix，并支持按 App 选择性部署。
- 生产环境当前使用密码方式 SCP/SSH，后续应迁移到短期凭据或 OIDC/密钥认证，并将部署脚本独立版本化。
